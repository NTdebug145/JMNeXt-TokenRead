# 论 Java Preferences 存储格式的不可移植性

## ——为什么本地加密令牌的提取必须经由 JVM

---

## 摘要

JMNeXt 桌面端把登录凭证（JWT）以 AES-256-GCM 加密后存进 `java.util.prefs.Preferences`，由 JDK 落到 Windows 注册表。要提取明文，必须先获得 JDK 写入前的原始 Base64 字符串，再用 AES-GCM 解密。本文论证：**这个中间字符串无法通过读取注册表原始值并自行解码获得**。注册表里保存的是 JDK 私有编码后的**存储层字符串**，它与应用逻辑层的**逻辑层字符串**长度不同、字符不同、边界行为无文档；反推注定失败，且随 JDK 版本漂移。唯一可靠的通道是让 JVM 自己用 `Preferences.get()` 解码。这不是工程偏好问题，而是编码契约不可分割的必然结果。

---

## 一、问题的提出

JMNeXt 桌面端的 `SecureStore` 与 `AuthStore` 共同实现了一个两阶段存储：

1. **应用层加密**：AES-256-GCM，密钥来自 `~/.config/jmnext/keys/jm_session_v1.key`，密文打包为 `[ivLen][iv][ciphertext+tag]` 并 Base64 编码。
2. **平台层持久化**：字符串交给 `Preferences.putString`，由 JDK 的 `WindowsPreferences` 落盘。

第二阶段之后，注册表里出现的字符串是：

```
/D/K/Zb/H/B/M/Mqdc/O957/Zofphrgem\thj/J8x/Pn\/Cr/Zjc5/...
```

共 1631 个字符。而应用原始写入的 Base64 字符串是：

```
DKZbHBMMqdcO957Zofphrgem/thjJ8xPn/CrZjc5...
```

共 1172 个字符。

**差值 459，不是随机误差，而是 JDK 存储层编码结构性的产物。** 问题由此提出：能否从注册表里的 1631 个字符，还原出应用逻辑层的 1172 个字符？

---

## 二、两个字符串的语义

先明确这两个字符串的本质区别。

**逻辑层字符串**，是 `SecureStore.encrypt()` 的返回值：

```kotlin
return out.toByteString().base64()
```

它是 Base64 编码的密文包，语义明确、长度符合 Base64 规范、可以直接 `Base64.decode()` 得到密文。这是应用**意图存进去的东西**。

**存储层字符串**，是 `Preferences.put` 之后注册表里实际出现的值。它不是应用写入的字符串的任何直接变形，而是**JDK 在写入过程中构造的一个中间表示**，既不属于应用的语义空间，也不属于 Windows 注册表的原生数据模型。

**这两个字符串之间不存在数学上公开的映射关系。** 本文余下部分论证的正是这一点。

---

## 三、反推为什么必然失败

### 3.1 转义规则不公开

OpenJDK 中负责这一层的是 `java.util.prefs.WindowsPreferences`，其编码逻辑写在私有静态方法里，既不在 `java.util.prefs` 的 Javadoc 中，也不在任何 JDK 规范文档中。JDK 官方对该层的承诺只有一条：

> 用 `Preferences.put(key, value)` 写入的值，用 `Preferences.get(key)` 读出来，得到原值。

**它从未承诺"注册表里那串东西长什么样"。** 这不是文档疏漏，而是设计选择：存储层编码属于实现细节，JDK 保留任意变更的权利。

### 3.2 边界条件不可推断

退一步说，即使承认"`\X` 与 `/X` 都表示字面 X"这个近似规律，也无法准确实现。原因在于：编码中还存在大量**边界条件**，无文档可依，只能靠数据分布反推，而样本从来不足以覆盖所有边界。

三次实证尝试说明了这一点：

| 尝试 | 采用的规则 | 还原后长度 | 结果 |
|---|---|---|---|
| 第一次 | 仅处理 `\X` | 1608 | `IV 长度非法：252` |
| 第二次 | 处理 `\X` 与 `/X` | 1157 | `Base64 padding 错` |
| 正确值 | 由 `Preferences.get()` 返回 | 1172 | 解密成功 |

第二次与正确值之间差 15 个字符。这 15 个字符对应的边界条件——连续转义符的处理、段尾的处理、空段的处理——**没有出现在样本里**，也就无法被归纳。它们不是分布稀疏，而是分布外。

**在 Base64 的解码语境里，长度不对齐不是"结果稍微偏差"，而是"完全无法解码"。** 这导致任何一种基于反推的实现，其失败模式都不是精度下降，而是灾难性失败。

### 3.3 编码随 JDK 版本漂移

`WindowsPreferences` 的实现自 JDK 1.4 以来经历过多次修改。存储层编码在任何一次修改中都**允许**改变，且变更无需公告。

这意味着：即使某个时刻反推出的规则是精确的，它也只在一个 JDK 版本的、一个平台、一种区域设置下成立。用户升级 JDK 后，同一份输入可能得到不同的存储层字符串，而反推规则不会报"规则不匹配"，只会让后续 Base64 解码产出乱码。**这是一类不会自暴露的错误。**

---

## 四、Java Preferences API 为什么可靠

`Preferences.get()` 之所以可靠，是因为**编码与解码在同一实现内部对称**。

JDK 的作者实现 `WindowsPreferences` 时，同时写了"逻辑字符串 → 存储字符串"和"存储字符串 → 逻辑字符串"两个方向。这两个方向在源码里成对出现，在同一版本内严格互逆。使用者只要不越出 API 边界——即不直接读写注册表——就永远看不到存储层。

这是一种典型的**封装契约**：API 的可见行为被明确保证，隐藏行为被明确不保证。契约的价值在于，只要遵守 API 边界，实现细节的变化对使用者透明。一旦越过 API 直接读注册表，就等于主动放弃了这个保证。

**从使用者的角度，这个契约成立的充要条件是：读写都经由同一个 JDK 版本的 `Preferences` API。** 本应用写入用 `putString`，读回时用 `get` —— 路径一致，编码和解码配对，因此可靠。

---

## 五、替代通道的不可行性

对于"提取本地 JWT"这个任务，可以设想的替代通道有四类，逐一评估：

**通道一：Python `winreg` 直接读注册表。** 读到的是存储层字符串，与逻辑层相差一个未知变换。已在第三节证明反推不可行。

**通道二：Python `pywin32` 或其他注册表库。** 同上，读到的仍是存储层。库的封装层次不影响操作系统给出的原始值。

**通道三：解析注册表中的 `REG_BINARY` 值。** 前提不成立。`Preferences` 写的是 `REG_SZ`，不是二进制。当前观测到的值类型是 `1`（`REG_SZ`），无二进制可解析。

**通道四：以 JVM 为桥梁（JPype、py4j、`subprocess` 调 `java`）。** 该通道可行，但**本质仍是让 JDK 解码**，只是把 Java 调用包装成 Python 调用。它不改变"必须经由 JVM"这一前提，只是把这一前提实现得更隐蔽。

由此可以得出一个更强的结论：**所有可行的方案在语义上都等价于"用 Java 解码"。** 所谓"用 Python 提取"，如果指"Python 从注册表读值并自行解码"，则不可行；如果指"Python 调用 JVM 完成解码，自己在更高层做后续处理"，则可行——但那已经不是纯粹的 Python 方案了。

---

## 六、结论

从 JMNeXt 桌面端的注册表中提取登录令牌，必须经由 JVM，理由可以归纳为三条：

1. **存储层字符串不是应用层字符串的简单变形。** 它是 JDK 私有编码的产物，两者长度、字符集、边界行为均不相同。

2. **存储层编码无公开规范、无文档、随版本漂移。** 反推其在理论上是欠定的（样本不足以覆盖边界），在工程上是脆弱的（版本一变即失效），在错误模式上是危险的（失败不自暴露）。

3. **`Preferences` API 是唯一同时保证正确性与稳定性的接口。** 它的可靠性来自编码与解码在同一实现内部的对称性，这是任何外部实现都无法复制的。

因此，"用 Python 直接解密注册表"这一构想，其失败不是工具选择的问题，而是**跨过了 API 契约边界**之后的必然结果。正确的分层是：**让 JVM 承担"存储层 ↔ 逻辑层"的翻译，Python 承担"逻辑层之上"的所有处理。** 这一分层既尊重了 JDK 的封装边界，也保留了自动化脚本的灵活性。

---

## 附：本文的适用范围

上述论证针对 Windows 平台上的 `java.util.prefs.Preferences`。在 Linux 上，JDK 默认实现是 `FileSystemPreferences`，存储格式为 XML，编码规则公开且稳定；在 macOS 上则是 `MacOSXPreferences`，落到 plist 文件。**不同平台上的存储层实现不同，"必须经由 JVM"这一结论在不同平台上强度不同。** 在 Windows 上它是绝对的；在 Linux 上，因为 `FileSystemPreferences` 的 XML 格式是自描述的、公开的，直接用 Python 解析理论可行；在 macOS 上介于两者之间。本文的一切论断仅在 Windows 平台的 `WindowsPreferences` 语境下成立。
